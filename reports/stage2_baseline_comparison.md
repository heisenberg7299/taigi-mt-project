## 量化結果

### 1. 否定詞保留率（negation_risk，30句）

| Baseline | 保留否定標記句數 |
|---|---|
| 1（辭典） | 26/30 |
| 2（Taigi-Llama） | 30/30 |

Baseline 1 有 4 句否定詞在替換過程中遺失或被錯誤處理——這是醫療情境**最不能接受的錯誤類型**（「我沒有胸痛」變成語意不明或反轉，等同誤報症狀）。

### 2. 人稱代詞「我」→「朕」的系統性錯誤

- 200句中含「我」的句子：147句
- Baseline 1 輸出出現「朕」（皇帝自稱，教育部辭典「我」詞條的其中一個釋義候選）：**130句**
- Baseline 2：0句（未出現此問題）

這證實 `PLAN.md` 記錄的教訓：辭典釋義是多義候選集合，不是翻譯對照表，直接反查必然在最高頻詞上系統性出錯。

### 3. 數字處理（numbers_id，20句）

| Baseline | 阿拉伯數字未轉換句數 |
|---|---|
| 1（辭典） | 16/20（幾乎不處理數字，原樣保留） |
| 2（Taigi-Llama） | 0/20（全部轉成台語數字讀法） |

Baseline 2 對數字的處理明顯更完整，但發現一個**唸法不一致**的問題需要在階段3安全檢查層特別處理：

```
302號病房  ->  三零二號病房   （逐位數唸法，符合病房號慣例）
501病房    ->  五百一號病房   （整數唸法，跟前者不一致）
```

醫療機器人若要唸病房號，這種不一致本身就是風險（病人/家屬可能聽錯房號）。**建議規則**：病房號、電話號碼一律用逐位數唸法，金額/步數/次數才用整數唸法，這條規則要在階段3的「數字一致性檢查層」明文寫死，不能依賴模型自己判斷。

## 結論與對 PLAN.md 階段6的影響

1. **辭典逐詞替換（Baseline 1）確認不可用**，即使規模擴大到12,372條也一樣——這不是資料量問題，是方法論問題（釋義≠翻譯）。這條路徑正式排除，辭典的角色收斂為「術語約束/未登錄詞fallback/翻譯後檢查」，不再考慮當主翻譯引擎。
2. **Taigi-Llama-2-Translator-7B（Baseline 2）品質足夠當研究階段的參考答案來源**，但 CC-BY-NC-SA-4.0 授權明確排除商用部署，只能當：
   - teacher model 產生 pseudo-label（給母語者校對後收進訓練集）
   - 階段6決策時的品質上限參考基準
3. 這把階段6的決策往 **(B) 或 (C)** 推：若要商用部署，需要 (B) 用 Taigi-Llama 產生的校對後資料做 LoRA 微調一個授權乾淨的底座模型，或 (C) 微調 mBART/NLLB 這類無 LLM 依賴、授權寬鬆的 encoder-decoder 模型。純規則/辭典系統（原本設想的方案）已被數據證偽，不再是候選。
4. 數字/病房號唸法一致性問題新發現，已記錄進階段3安全檢查層的具體規則，不能只靠翻譯模型自行決定。
